## Verification before parity sign-off

- Targeted unit tests cover term-limit computation and meeting-document schema/PDF content; focused ESLint passed after edits.
- Existing browser E2E covers the consent agenda and board minutes creation, approval, persistence, package appearance, and audit; the test is being extended for the newly exposed fields and selected-day route.
- Authenticated local E2E against the development Supabase passed Calendar meeting documents 3/3 and Recruitment 11/11 on 2026-11-12. The separate invitation acceptance test passed: a Chair role propagated to the fifth active member of a Roots workspace. The multi-role Calendar test passed on the rebuilt application: five active Roots seats, Chair draft editing, confidential file upload, past-day minutes access, stale-save rejection, denied direct API writes and persisted Executive task-status change. Browser tests against a deployed staging build and a side-by-side UI comparison with both source HTMLs are still required. No claim of complete parity is made from code inspection alone.
- The standalone calendar prototype exposes seven RSVP/attendance states and three action statuses. These are now represented in the meeting document editor; the staging deployment must be exercised to verify them with live data.
- Committee-agenda structured action review now has a focused unit test; its interaction in the deployed staging UI remains to be checked.
- The Calendar role model is now implemented separately from global Team roles. Administrator sees all tabs and manages the calendar. Executive Director / COO sees Dashboard, Calendar, Meetings, Workflows, Packages and Directory and may advance workflow task status. Committee Chair sees Dashboard, Calendar, Packages and Directory and may edit meeting documents and add/remove confidential package files. Board Member sees the same limited tabs and may RSVP and read approved package documents. Server actions enforce these capabilities, and database triggers reject unauthorized direct `template_instances` writes. The source prototype has an unguarded Delete meeting button on its Meetings screen for Executive users, even though its own role hint says “view”; the application keeps deletion restricted to administrators as a security correction.
- The five Calendar role migrations through `20261112225000_board_calendar_unchanged_task_statuses.sql` were applied to the linked development project `tweeaxnawemykedrxsar` with `supabase db push` (exit 0). The last migration allows unchanged generated blank or legacy task statuses while requiring any newly selected status to be a supported value. The production database has not been changed in this task.
- The prototype's “Send invitation” action is only a demo that adds a contact and displays “Invitation sent (demo).” The application sends a real Team invitation and persists the Calendar role on acceptance. This is a functional improvement over the demo behavior.
- `template_instances` stores the whole calendar in one JSON row. Existing RLS denies raw `template_instances` SELECT/UPDATE for non-administrators. The server reads organization-scoped rows only after checking active workspace membership. Board Member sees approved documents, safe dates and directory fields; Chair also sees drafts and package fields needed for document work; Executive sees meetings and workflow tasks but not drafts or settings. Restricted saves compare the submitted role projection against a fresh role projection, merge only the permitted fields into the full row, preserve metadata and reject stale client versions. The server's save response is projected again. Any future fields added to the calendar must be explicitly reviewed for each role before inclusion in these projections.
- Board Calendar full report and meeting-document branded PDFs now use the request locale. French static headings, table labels, dates and states are translated while preserving organization brand and member-entered text; focused HTML generation tests cover both paths, and a PDF extraction test verifies French text and brand in the rendered report.
- The remote development Supabase rejects `@example.com` signup addresses and does not expose the Mailpit capture API used by the existing registration E2E. The old signup-to-email-confirmation test failed on that environmental dependency; an admin-confirmed invited-user E2E covers the real invite RPC, acceptance, role propagation and five-seat limit without claiming email delivery was tested.
